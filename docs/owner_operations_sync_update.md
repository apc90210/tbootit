# Панель управления операциями владельца (Owner Operations, Sync & Schema Guard)

**Стадия:** STAGE 08D-R1R5  
**Статус:** Активна  
**Назначение:** Документация архитектуры, системы защиты схемы БД и руководства оператора для панели `/system/operations`.

---

## 1. Архитектурные правила и направления потоков

В системе ТехноРебут действует жесткое разделение потоков кода и бизнес-данных:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                             АРХИТЕКТУРНЫЙ КОНТРАКТ                          │
├─────────────────────────────────────────────────────────────────────────────┤
│ 1. КОД:          LOCAL DEV ───► Git (origin/main) ───► VDS (update script)  │
│ 2. БИЗНЕС-ДАННЫЕ: VDS ────────► LOCAL DEV (one-way business snapshot sync)   │
│ 3. СТРОГИЙ ЗАПРЕТ: LOCAL DEV ──╳──► VDS (перезапись данных VDS запрещена)  │
└─────────────────────────────────────────────────────────────────────────────┘
```

1. **Код (Code Flow):** Разработка ведется исключительно на локальной рабочей станции (`LOCAL DEV`). Изменения коммитятся в Git, отправляются в `origin/main` и развертываются на сервере VDS с помощью скрипта `deploy/production/update_code_only.sh`.
2. **Бизнес-данные (Business Data Flow):** Единственным каноническим источником истины для товаров, продаж, ремонтов, клиентов, медиафайлов и листингов является продуктивный сервер `VDS`. Данные копируются строго в одном направлении: `VDS -> LOCAL`.
3. **Абсолютный запрет обратной передачи данных:** Локальная база SQLite и локальные файлы хранилища ни при каких обстоятельствах не загружаются на VDS. На VDS заблокирован запуск любых синхронизаций и обновлений.

## 2. Локальный исполнитель операций (Local Ops Runner)

Контейнер `admin-shell` изолирован от хостовой системы (не содержит SSH-ключей хоста и не имеет доступа к сокету Docker). Для безопасного выполнения операций реализован хостовый демон-исполнитель:

- **Файл исполнителя:** `scripts/local_ops_runner.py`
- **Каталог запросов:** `data/dev-ops/requests/<job_id>.json`
- **Каталог статуса:** `data/dev-ops/status/current.json`, `lock.json`, `last_sync.json`, `last_update.json`
- **Журнал аудита:** `data/dev-ops/audit_log.json`

### Блокировки и предотвращение гонок (Concurrency Lock)
- Перед началом любой операции создается атомарный файл блокировки `data/dev-ops/status/lock.json`.
- Любой параллельный запрос возвращает HTTP 409 Conflict («Другая операция уже выполняется»).
- Предусмотрено авто-снятие устаревших блокировок (stale lock recovery), если с момента захвата прошло более 15 минут.

## 3. Защита схемы базы данных (DB Schema Guard)

Для предотвращения падения продуктивной базы данных SQLite при развертывании кода внедрен автоматический Schema Guard:

### Компоненты:
1. **Канонический контракт схемы:** `deploy/production/schema_contract.json`
   - Содержит отсортированный, нормализованный снимок всех 23 таблиц, типов колонок, nullability, primary keys, foreign keys и индексов.
   - Фиксируется контрольная сумма SHA256 (канонический хеш: `ce11b10dc33ecd3ab6804bf65e12fc55a840ce3f308b5cd2da4a6869b8e904d7`).
2. **Инструмент валидации:** `scripts/db_schema_contract.py`
   - Извлекает схему напрямую из AST/моделей SQLAlchemy в `core/app/models.py`.
   - Интроспектирует живую базу SQLite (как локально, так и на VDS через SSH).
   - Выполняет консервативное структурное сравнение: любое расхождение (добавление таблицы, колонки, изменение типа или nullability) регистрируется как несовместимость.
3. **Флаг совместимости:** `deploy/production/deployment_compatibility.json`
   - Отслеживаемый в Git конфигурационный файл.
   - Если `requires_manual_migration == true` или обнаружены структурные изменения схемы, кнопка `[ UPDATE VDS ]` автоматически блокируется (UI disabled, API возвращает 400 Bad Request).

## 4. Панель управления `/system/operations`

Доступна только владельцу (роль `OWNER`, проверяется через mTLS-сертификат или системную авторизацию).

### Элементы интерфейса:
1. **Индикаторы окружения:**
   - Значок `[ DEV ОКРУЖЕНИЕ (LOCAL) ]` (зеленый) или `[ VDS PRODUCTION ]` (красный).
   - Значок Schema Guard: `[ СХЕМА: СОВМЕСТИМА ]` или `[ СХЕМА: РУЧНАЯ МИГРАЦИЯ ]`.
2. **Кнопка 1: `[ Синхронизировать данные с VDS ]`**
   - Создает snapshot на VDS (`python3 scripts/vds_backup.py`).
   - Загружает snapshot по SCP в `.local-recovery/`.
   - Проверяет SHA256 контрольную сумму.
   - Сохраняет локальную pre-sync safety копию.
   - Перезапускает локальные контейнеры и применяет базу и фотографии.
   - Сверяет 100% паритет всех таблиц.
3. **Кнопка 2: `[ UPDATE VDS ]`**
   - Проверяет чистоту рабочего дерева Git и отправку коммитов в `origin/main`.
   - Проверяет Schema Guard (если схема изменена, операция заблокирована).
   - Подключается к VDS по SSH, создает VDS safety backup.
   - Запускает `deploy/production/update_code_only.sh origin/main`.
   - Пересобирает и перезапускает сервисы, сохраняя базу данных и фотографии.
   - Проверяет healthcheck всех 6 сервисов.
4. **Консоль реального времени:**
   - Отображает номер шага (1 из 10), прогресс-бар и логи выполнения с авто-прокруткой.
5. **Журнал аудита:**
   - Таблица последних операций со ссылками на коммиты и архивные бэкапы.

## 5. Защита от запуска на VDS (Environment Guard)

В продуктивном окружении VDS:
- Наличие файла `/srv/technoreboot/data/.technoreboot_production_data`.
- Переменные `ENVIRONMENT=production`, `APP_ENV=production`.
- Отсутствие файла `.technoreboot_local_dev`.

При открытии панели на VDS:
- Выводится предупреждающий баннер красного цвета.
- Обе кнопки действий переведены в состояние `disabled`.
- Любой прямой вызов `POST /admin-api/system/operations/sync` или `POST /admin-api/system/operations/update` возвращает HTTP 403 Forbidden.
