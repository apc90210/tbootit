# Архитектура и Руководство: Быстрый откат VDS (Fast Rollback)

## 1. Концепция и Принципы

Быстрый откат VDS (Fast Rollback) в системе **ТехноРебут** предназначен для мгновенного возврата продуктивного сервера к последней заведомо рабочей версии кода и контейнеров без потери актуальных данных, внесенных пользователями или созданных в продакшене.

### Фундаментальные инварианты:
1. **Откат ТОЛЬКО КОДА (Code-Only Rollback):**
   - Нормальный быстрый откат переключает версию кодовой базы (Git commit) и перезапускает сервисные контейнеры Docker.
   - **НИ ПРИ КАКИХ ОБСТОЯТЕЛЬСТВАХ** нормальный откат не заменяет и не перезаписывает рабочую базу данных SQLite (`technoreboot.db`) и не откатывает пользовательские медиафайлы (`data/storage/`).
   - Все продажи, заказы на ремонт, созданные товары и загруженные фотографии, созданные после обновления, остаются в полной сохранности.

2. **Защита схемы БД (Rollback Schema Guard):**
   - Перед переключением кода интроспектируется живая схема базы данных на VDS.
   - Сравнивается контракт схемы живой БД с контрактом схемы целевой версии отката (`target_checkpoint["previous_schema_sha256"]`).
   - Если контракты не совпадают (например, при обновлении была изменена таблица или добавлено обязательное поле), откат **ЖЕСТКО БЛОКИРУЕТСЯ** (`ROLLBACK BLOCKED`).
   - Для версий с изменением структуры базы требуется отдельная контролируемая процедура миграции/восстановления.

3. **Предварительный аварийный бэкап (Disaster Safety Backup):**
   - Непосредственно перед переключением контейнеров создается полный бэкап текущего состояния VDS (`TECHNOREBOOT_BACKUP_*.zip`), чтобы гарантировать возможность аварийного восстановления.

4. **Локальный контроль Владельца (Owner-Only & Local-Only):**
   - Кнопка и API отката доступны **исключительно** Владельцу (`is_owner=True`).
   - Откат разрешен **только из локальной среды DEV** (`/system/operations`), вызовы непосредственно на VDS возвращают `403 Forbidden`.

## 2. Модель Checkpoint Релиза (Release Checkpoint)

Перед каждым обновлением VDS (`UPDATE VDS`) автоматически создается контрольная точка релиза (`checkpoint_<timestamp>_<commit>`):

```
.local-recovery/vds-releases/<checkpoint_id>/
├── checkpoint.json          # Полный манифест контрольной точки
├── business-backup.zip      # Локальная верифицированная копия бэкапа данных VDS
└── business-backup.sha256   # Контрольная сумма SHA-256
```

### Манифест Checkpoint (`checkpoint.json`):
- `checkpoint_id`: уникальный идентификатор (например, `checkpoint_20260912_163204_e2805f1f`).
- `created_at`: метка времени создания (ISO-8601 UTC).
- `status`: `COMPLETED`.
- `previous_head`: коммит, на котором VDS работал стабильно до обновления.
- `target_head`: коммит, на который выполняется обновление.
- `previous_schema_sha256`: SHA-256 контракта схемы БД до обновления.
- `business_backup_file`: имя созданного архива бэкапа на VDS.
- `business_backup_sha256`: контрольная сумма архива бэкапа на VDS (верифицирована с локальной копией).
- `business_counts`: количество товаров, продаж, ремонтов, фото и внешних объявлений.
- `storage_tree_sha256`: хэш дерева файлов медиа-хранилища.
- `ca_sha256`: хэш корневого сертификата авторизации.
- `rollback_allowed`: флаг допустимости отката без миграции БД (`true`/`false`).
- `previous_image_ids`: хэши Docker-образов всех 6 сервисов до обновления.

---

## 3. Политика удержания (Retention Policy)

- Система хранит минимум **3 последних контрольных точки** на локальной машине и на VDS.
- Контрольная точка, помеченная как последняя подтвержденная рабочая версия (`last_known_good_vds_release.json`), **никогда не удаляется**.
- При создании новых контрольных точек устаревшие чекпоинты (сверх лимита) автоматически очищаются.

---

## 4. Сценарии отката

### Сценарий А: Автоматический откат при сбое обновления (Auto-Rollback)
Если в процессе `UPDATE VDS`:
- Команда сборки или запуска контейнеров на VDS завершилась с ошибкой;
- Хотя бы один из 6 контейнеров не перешел в состояние `healthy`;
- VDS стал недоступен по HTTPS/mTLS;

Система автоматически:
1. Выполняет `git checkout -f <previous_head>`.
2. Перезапускает продакшен-контейнеры предыдущей версии.
3. Проверяет восстановление статуса `healthy` всех 6 сервисов.
4. Фиксирует статус `UPDATE_FAILED_ROLLBACK_SUCCESS` в журнале аудита.
5. Данные и база VDS остаются 100% нетронутыми.

### Сценарий Б: Ручной откат по решению Владельца
1. Владелец открывает `/system/operations` в локальном браузере.
2. В карточке **«Быстрый откат VDS»** отображается последняя рабочая версия и статус доступности отката.
3. Владелец нажимает кнопку **«Откатить VDS к последней рабочей версии»**.
4. В модальном окне подтверждения отображаются:
   - Исходный коммит и целевой коммит отката.
   - Подтверждение совместимости схемы БД.
   - Предупреждение о том, что данные БД затронуты не будут.
5. После подтверждения задача ставится в очередь, бегун выполняет откат с проверкой сервисов и обновляет статус.
