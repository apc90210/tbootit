# Техническая документация: Stage 07E-R1 — Восстановление нового сервера и Disaster Recovery

## 1. Назначение и цели этапа

**Цель:** Доказать и гарантировать детерминированное восстановление работоспособного контура ТехноРебут на чистом сервере/VM с Debian 12 на основе только исходного кода из Git и одного архива резервной копии ТехноРебут (`TECHNOREBOOT_BACKUP_*.zip`), без какой-либо зависимости от старого работающего сервера.

### Ключевые гарантии этапа:
1. **Полная независимость:** Восстановление не требует доступа к старому серверу или работающему веб-интерфейсу.
2. **Непрерывность доверия PKI (Auth Continuity):** Восстановленный корневой удостоверяющий центр (CA) признаёт ранее выданный сертификат Владельца (`OWNER`), исключая необходимость перегенерации CA или перевыпуска сертификатов.
3. **Безопасность восстановления (Security & Safe Staging):** Защита от уязвимости Zip Slip (блокировка `../` и абсолютных путей), строгая предварительная проверка манифеста и схемы, двухэтапная распаковка во временную staging-директорию с валидацией SQLite БД (`PRAGMA integrity_check`).
4. **Сохранение стабильности файловых дескрипторов Docker:** Пофайловая синхронизация (`_safe_sync_dir`) для предотвращения разрыва Docker bind-mounts.
5. **Чёткое разделение двух политик восстановления:**
   - *Политика A (Обычное восстановление через веб `/backups`):* Восстанавливает только бизнес-данные (БД, медиа, Авито), **сохраняя текущие активные сертификаты `data/auth`**, чтобы не разрывать сессию Владельца и не откатывать недавно созданные сертификаты.
   - *Политика B (Аварийное восстановление чистого сервера):* Восстанавливает всю систему целиком, **включая `data/auth`** из бэкапа, оживляя исторический CA и сертификат Владельца.

## 2. Архитектура и компоненты

### Точки входа:
- `scripts/bootstrap_restore.sh` — POSIX Bash-скрипт предварительной проверки ОС (Debian/Ubuntu), зависимостей (Python 3, cryptography, Docker) и запуска движка восстановления.
- `scripts/bootstrap_restore.py` — Кроссплатформенный детерминированный движок аварийного восстановления, реализующий валидацию архива, защиту от path traversal, staging, синхронизацию каталогов, управление docker compose и верификацию данных.

## 3. Политики безопасности и непрерывности PKI

### Предотвращение Zip Slip:
При чтении любого файла из ZIP-архива проверяются все элементы пути (`namelist`):
```python
for name in namelist:
    if name.startswith("/") or name.startswith("\\"):
        raise SecurityError("Absolute path forbidden")
    if ".." in Path(name).parts:
        raise SecurityError("Directory traversal forbidden")
```
При обнаружении любого подозрительного файла операция прерывается до создания или изменения файлов на диске.

### Непрерывность доверия сертификата Владельца:
1. Восстанавливаются файлы `auth/ca/ca.crt` и `auth/ca/ca.key`.
2. Восстанавливаются `auth/certificates/owner.crt`, `owner.key`, `owner.p12`.
3. Восстанавливается `auth/registry.json` со статусом `ACTIVE` для Владельца и сохранением статусов отозванных сертификатов (`REVOKED`).
4. Менеджер авторизации (`AuthManager`) при старте видит существующие валидные сертификаты CA и Владельца и **ни в коем случае не генерирует новый CA**.
5. Шлюз `gateway` (Nginx mTLS на порту 8443) проверяет входящий клиентский сертификат против `auth/ca/ca.crt` и внутреннего эндпоинта `admin-shell:8010/internal-auth/verify`. Запросы с сертификатом Владельца успешно проходят аутентификацию (HTTP 200), а запросы без сертификата отклоняются (HTTP 403).

Все тестовые прогоны аварийного восстановления запускаются в изолированных временных каталогах операционной системы (`tempfile.mkdtemp` / `tmp_path`), что на 100% защищает рабочую локальную базу данных `C:\tbootit\data\db\technoreboot.db` и действующий PKI от любых модификаций (проверено побайтовым хешированием SHA256 до и после тестов).

## 6. Подтверждение на реально работающем изолированном Docker-стеке (Stage 07E-R1-R1)

Для исключения любых сомнений в работоспособности восстановленной системы реализовано сквозное подтверждение на **полноценно запущенном втором Docker-стеке**:

1. **Параллельный запуск на альтернативных портах:**
   - Шлюз mTLS: `9443:8443` (вместо живого `8443`)
   - Core API: `9000:8000` (вместо живого `8000`)
   - Admin-Shell: `9011:8010` (вместо живого `8011`)
   - Avito Module: `9020`, `9061`
   - Inventory Module: `9030`
   - Repairs Module: `9040`
   - Отдельный проект: `technoreboot-recovery-<run-id>`
   - Отдельные имена контейнеров: `technoreboot-recovery-<service>-<run-id>`

2. **Неопровержимое различие между живым контуром и восстановленным:**
   - **Живой рабочий контур (порт 8443):** 50 товаров (результат свежего импорта первой страницы после сброса каталога).
   - **Восстановленный контур (порт 9443):** 227 товаров из резервной копии, 50 продаж, 66 ремонтов, 490 фотографий.
   - Запросы к `https://127.0.0.1:9443/inventory/products` отдают полный каталог из 227 товаров с фотографиями.

3. **Собственный контур mTLS:**
   - Шлюз 9443 монтирует сертификаты и CA исключительно из изолированной директории `.recovery-test/<run-id>/data/auth`.
   - Запросы с сертификатом Владельца возвращают HTTP 200 OK на всех закрытых маршрутах (`/backups`, `/certificates`).
   - Запросы без сертификата отклоняются шлюзом (HTTP 403 Forbidden).

4. **Гарантия нетронутости боевого локального стека:**
   - SHA256 живой базы данных `data/db/technoreboot.db` до и после теста совпадает.
   - SHA256 живого CA `data/auth/ca/ca.crt` до и после теста совпадает.
   - Число перезапусков живых контейнеров: **0** (контейнеры не останавливались и не перезапускались).
